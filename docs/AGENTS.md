# Инструкция для агентов и контрибьюторов

Цель документа: любой агент, человек или CI-бот может продолжить работу с этого репозитория без устного контекста.

## 1. Обязательный протокол перед изменениями

```bash
git status                      # рабочая ветка, нет ли незакоммиченного
git log --oneline -n 20         # что делали до вас
cat docs/CHANGELOG.md | head -n 60
cat docs/ARCHITECTURE.md        # карта кода
npm ci                          # если ещё не установлено
npm test                        # базовая линия должна быть зелёной
```

Прочитайте `docs/CONTENT_INDEX.md`, чтобы понять, какой контент уже есть, и `docs/ROADMAP.md` — чтобы выбрать следующую задачу.

## 2. Правила изменений

1. **Одна логическая задача = один коммит по Conventional Commits.**
   Формат: `тип(область): описание` на русском или английском, в императиве.
   - `feat(grammar): добавить тему Present Perfect`
   - `fix(listening): исправить ответ на вопрос 2`
   - `chore(release): v0.2.0` — ставится автоматически, вручную не создавайте.
2. **Любое изменение функциональности сопровождается документацией** в том же коммите:
   - архитектура/каналы/структура → `docs/ARCHITECTURE.md`;
   - новый контент → `docs/CONTENT_GUIDE.md` + `npm run docs:generate`;
   - процесс сборки/релиза → `docs/RELEASING.md`;
   - заметное для пользователя изменение → запись в `docs/CHANGELOG.md` (для релизов дописывается автоматически);
   - пользовательские сценарии → `docs/USER_GUIDE.md`;
   - приоритеты и новые задачи → `docs/ROADMAP.md`.
3. **Не редактируйте `docs/CONTENT_INDEX.md` руками** — он генерируется.
4. **Не коммитьте `dist/`, `node_modules/`** — они в `.gitignore`. `package-lock.json` коммитится и используется CI (`npm ci`).
5. **Не меняйте `version` в `package.json` вручную** для обычных задач: этим управляет workflow Release.
6. **Коммиты с `[skip ci]`** допускаются только для служебных правок документации, которые не влияют на сборку.
7. **Секреты и токены** не добавляйте в репозиторий. Для релиза используется встроенный `GITHUB_TOKEN`.

## 3. Чек-лист после изменений

```bash
npm test                 # node:test + валидация контента
npm run docs:generate    # обновить индекс и статистику
npm run docs:check       # убедиться, что документация синхронна коду
git status               # просмотреть изменённые файлы
git diff                 # самопроверка диффа
```

Если меняли код интерфейса — запустите `npm start` (или `npm run preview` для проверки в браузере) и пройдите основные экраны. Smoke-тест интерфейса в jsdom выполняется автоматически в `npm test`. Если меняли данные — проверьте, что новый ID не дублируется и все ответы в диапазоне вариантов.

## 4. Где что менять

| Задача | Файлы |
|---|---|
| Новая тема грамматики | `src/data/grammar.js`, затем `npm run docs:generate` |
| Новый урок аудирования | `src/data/listening.js` |
| Новые слова | `src/data/vocabulary.js` |
| Логика экрана / навигация | `src/renderer/app.js` (`routes.*`) |
| Стили, темы | `src/renderer/styles.css` |
| Автообновление, IPC, меню | `src/main.js`, `src/preload.js` |
| Иконка | `scripts/make-icon.js` → `npm run icon` |
| CI | `.github/workflows/ci.yml` |
| Релиз | `.github/workflows/release.yml`, `docs/RELEASING.md` |

## 5. Соглашения по коду

- JavaScript без фреймворков; браузерные модули не используются, данные — глобальные объекты.
- В рендерере любой пользовательский текст прогоняйте через `escapeHtml()` перед вставкой в `innerHTML`.
- Новые строки интерфейса — на русском; учебный контент — английский + перевод.
- Все цвета — через CSS-переменные, чтобы работали обе темы.
- Не добавляйте зависимости без необходимости; если добавили — обновите `docs/ARCHITECTURE.md` и `package.json`.

## 6. Проверка данных (обязательные инварианты)

`npm test` проверяет:

- уникальность `id` тем, уроков и наборов слов;
- наличие объяснения (> 400 символов), 3+ примеров, 3+ упражнений, блока `pitfalls`;
- корректность `answer` (число в диапазоне вариантов) и отсутствие дублей вариантов;
- длину текстов аудирования (≥ 150 символов) и наличие перевода/вопросов;
- отсутствие `<script>` и `onerror=` в HTML-контенте;
- наличие обязательных файлов и иконки.

## 7. Зависимости

Dependabot обновляет npm-пакеты и GitHub Actions раз в неделю/месяц, но **только patch/minor**:
мажорные версии Electron, electron-builder и electron-store требуют миграции кода
(electron-store 9+ — ESM-only) и обновляются вручную отдельным PR с проверкой сборки.

## 8. Релиз

Автоматически: merge/push в `main` → версия, тег, сборка, GitHub Release.
Вручную: `Actions → Release → Run workflow` (`patch` / `minor` / `major` / `auto`).
Подробности и troubleshooting — `docs/RELEASING.md`.

## 9. Что делать, если CI упал

| Симптом | Действие |
|---|---|
| `Валидация данных` | Прочитайте вывод: указан конкретный id и поле. Исправьте данные, повторите `npm test`. |
| `docs:check` упал | Запустите `npm run docs:generate` и закоммитьте изменения `docs/CONTENT_INDEX.md` / `README.md`. |
| Сборка Windows упала на `electron-builder` | Проверьте, что версия в `package.json` не занята тегом; перезапустите workflow. |
| `latest.yml` отсутствует в релизе | Убедитесь, что в `electron-builder.yml` есть `publish: provider: github` и сборка шла с `GH_TOKEN`. |
| Клиент не видит обновление | Проверьте тег `vX.Y.Z`, `latest.yml` в релизе и что новая версия выше установленной. |
